# Agent 回合分析

## 总览的 Codex 子代理

当前筛选范围有已确认的子代理启动或用量时，总览在工具与模型用量之后、活动日历之前显示「Codex 子代理」卡。启动数按筛选日期内新建的子代理线程去重。Tokens 来自同一份有效账本，已包含在总览用量中。模型筛选下只统计有匹配用量的子代理。自动审批和无法确认角色的记录仍按原口径进入总览。

卡片同时显示 Tokens、估算费用和各自占比。卡片横条以当前筛选的 Codex 合计为分母。按对话展开后，横条以当前子代理合计为分母。费用取已有账本估算，有未计价用量时费用小计和已知费用占比以 ≈ 标记，缺少可用估算或分母为零时相应读数显示 —。

「按对话查看」使用日志中可核对的父线程关系，展示各子代理的模型和用量。主代理的回合数按能确认用户输入的回合开始事件去重，含随后中断的回合。未能确认用户输入或父会话链的记录不推断。统计保留已采集的证据，扫描仍存在的日志可补齐历史。

入口：统计窗口 → 速度（English: Speed）。日期使用窗口共用范围，模型筛选独立于费用明细。列表支持耗时、时间戳正反序、速度和推理量排序；分页不影响顶部指标或速度图。模型和日期变化保留排序，仍在范围内的选中回合保持选中。

## 指标口径

- 平均速度：范围内生成 tokens 总和 ÷ 回合耗时总和。生成量已包含推理，不含输入或缓存；耗时包含工具和等待。这是回合吞吐，不是模型的纯解码速度。
- 平均首 token 等待：日志 `time_to_first_token_ms` 的算术平均；缺失值不参与平均。它是 Codex 记录的首 token 时间，不等于首个用户可见字符时间。
- 平均推理量：有推理记录的回合，其 reasoning tokens 的算术平均。明确的零参与平均，未知值显示 `—`。覆盖数量在指标帮助中。
- 工具等待：顶层 call 完整记录的时间戳到匹配 output 时间戳，求区间并集。这是日志时间估算；不用 `create_time` 或后台命令完整生命周期。缺失配对时不可用；剩余时间不命名为模型生成时间。
- 速度图按北京时间的回合开始时间分组。单日按小时，2–7 天按日，8 天及以上和全部时间按周。周从周一开始，首尾仅覆盖所选日期内的部分。每组至少 3 个回合时，箱体覆盖第 25–75 百分位，刻线是中位数，细线延伸到常规范围内的实测值，离群回合单独显示。只有 1–2 个回合时保留各自的时间和速度，空时段留白。
- 悬停箱体查看时间范围、回合数、速度区间和典型速度。点击箱体筛出该时段并选中最接近中位数的实测回合，点击散点打开该回合。点击「显示全部」恢复完整列表。时段筛选只作用于列表与明细。
- Fast 闪电来自明确的模式记录。Codex 采用该回合开始时记录的所选模式，Claude 采用各回复一致报告的模式。总览累加有效记录中的 Fast tokens，明细和速度仅在对应记录显示标记。重新扫描仍保有模式证据的日志可补齐历史回合。

## 数据与边界

SQLite schema v4 增加独立 `codex_turns` 表，不写入费用用量表。扫描复用配置中的 Codex 路径及额外路径；文件大小和修改时间未变化时复用解析缓存。IPC `codexTurns` 返回日期/模型范围中的全部回合及日期范围模型目录，原生页首次访问才查询，扫描后刷新已加载页面。

支持含 `task_started`、`task_complete.duration_ms` 和可按 `response_id` 去重、与回合总量对账的 `token_usage_record` 的已完成主回合。旧版缺失可靠时间或用量的日志、未完成回合、混合模型、子 agent、OpenClaw、fork/多 session 回放不纳入。源日志删除或后来损坏时保留已存历史。存储只有项目短名、模型、身份、时间和计数，不保存 prompt、回复或工具文本。

### Hooks 调研

生命周期 hooks 能补充回合开始/结束、工具调用前后等时间边界。若只覆盖这些事件，不能直接获得每次模型请求的首/末 token 时间。Gemini CLI 的 `BeforeModel` 在请求前触发，`AfterModel` 在流式响应的每个 chunk 触发，因此具备进一步采集请求时间和客户端可观测输出时间的条件。来源：[Gemini CLI hooks reference](https://geminicli.com/docs/hooks/reference/#model-hooks)。

生成阶段速率需要同一请求的首个有效 token、最后 token 时间以及口径匹配的 token 数；首 token 前的等待仍可能含排队、网络、输入处理及内部推理，不能仅凭时间拆出服务端推理。Claude Code 的同步 prompt hooks 会阻塞模型处理，测量代码也会增加开销；应优先使用已有运行时指标，需要补充时再配置只写时间和 ID 的轻量采集器。来源：[Claude Code hooks reference](https://code.claude.com/docs/en/hooks#userpromptsubmit)。本次没有安装 hooks 或修改 agent 配置。

### 缺失来源的最小补采方案

覆盖表中的补采建议可落到同一组本地事件（方案，尚未安装采集器）：

- 回合开始：agent、session ID、稳定 turn ID、主/子 agent 身份、UTC 时间及单调时钟起点。
- 请求结束：turn ID、request ID、实际返回模型、最终输出/推理 token 计数及二者是否包含；重复上报按 request ID 更新。
- 回合结束：同一 turn ID、完成/取消/错误状态、单调时钟耗时；只有完成且用量完整的回合进入平均速度。
- 首/末 token 和工具起止是可选扩展。只有客户端提供相应事件才能测量；普通 prompt/stop hook 不能补出缺失的请求计数或首 token 时间。

优先从原有日志补读字段，其次使用客户端正式事件/导出接口。必须新增 hook 时，只写本地时间、ID 和计数，不向模型注入测量提示。仅有会话汇总的历史数据无法倒推出回合速度；补采从启用后生效。
